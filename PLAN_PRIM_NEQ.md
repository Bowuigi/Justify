# Expose `neq` as the built-in `prim_neq` relation

## Final goal

Expose the existing `neq` goal as a built-in relation `prim_neq(left, right)`. The relation has one implicit rule named `prim`. It works in rule premises and as a top-level Query relation. Its name is reserved. Pending disequality constraints appear in QueryResult solutions, and satisfied constraints disappear at presentation time. The feature also covers the packages that consume the relation: validator, CLI, TeX extractor, and playground.

## Relevant context

### Current branch state

- `neq` is implemented in `packages/inferencer/mk.ts` and its direct tests pass.
- `packages/inferencer/tests/prim-neq.test.ts` contains the acceptance tests for `prim_neq`. They currently use `it.fails`.
- `formats/query-result.jtd.json`, `packages/core/codegen/query-result-types.d.ts`, and `docs/QueryResult.md` already carry the `constraints.neq` field.

### Important gap

`walkConstraints` in `packages/inferencer/mk.ts` resolves constraint terms but keeps every constraint. The tests in `packages/inferencer/tests/prim-neq.test.ts` require that a constraint which becomes trivially true after later bindings is absent from the QueryResult. Pruning must happen at presentation time. Do not remove constraints from the solver state.

### File roles

- `packages/inferencer/mk.ts`: goals, `State`, `Constraints`, `walkConstraints`, `run`.
- `packages/inferencer/mk-codegen.ts`: `toRelationStore`, the bridge from System premises to goals.
- `packages/inferencer/lib.ts`: `performQuery`, which converts solver states into QueryResult solutions.
- `packages/validator/modules/*.ts`: hand-written validation passes.
- `packages/validator/driver.ts`: calls the fused validation functions.
- `packages/validator/codegen/fused.ts`: generated by `npm run codegen`. Do not edit it by hand.
- `packages/core`: generated types and JSON validators. The QueryResult format already has `constraints.neq`.
- `packages/cli/render.ts`: `prettySolution` renders human-readable solutions.
- `packages/tex-extractor/lib.ts`: `extractTeX` emits macros; `extractDerivationTeX` renders derivation trees.
- `packages/playground/lib/try.ts`: converts solutions to Try data.
- `packages/playground/components/try-tool.tsx`: renders Try results.

### Decisions

- `prim_neq` is implicit in every System. Systems do not declare it.
- The relation accepts exactly two terms of any syntax category.
- `prim_neq` is valid in premises and as a Query relation.
- The name `prim_neq` is reserved. A System that declares a relation with that name is invalid.
- The derivation node has `relation: "prim_neq"`, `rule: "prim"`, resolved `args`, and empty `premises`.
- Pending constraints stay in solver state. `walkConstraints` prunes constraints that the final substitution makes trivially true.
- Documentation changes are out of scope for this plan.

## Methodology

The plan uses acceptance-test-driven development. Each phase starts with tests that state the required behavior. Then implement until the tests pass.

1. Read the files named in the phase.
2. Assume that all earlier phases are complete. Implement only one phase at a time.
3. Write or convert the phase tests first. Run them and observe the expected failures.
4. Implement the smallest production change that makes the tests pass.
5. Run the focused test project.
6. Run lint, then formatting, then the formatting check.
7. Review the diff. It must contain only changes for the current phase.
8. Report the result to the user.
9. Stop after one phase.

## Plan phases

### Phase 1: Implement the built-in relation in the inferencer

#### Goal of phase 1

Make the existing `prim_neq` tests pass. Add the built-in relation to the inferencer and prune satisfied constraints from presented solutions.

#### Description of phase 1

In `packages/inferencer/mk-codegen.ts`, add a `prim_neq` entry to the relation store. The entry takes two arguments and returns `MK.wrapLogs('prim', 'prim_neq', args, MK.neq(args[0], args[1]))`. The built-in takes precedence over a System relation with the same name.

In `packages/inferencer/mk.ts`, change `walkConstraints` so it drops a constraint when no variables are present on either term of the already-walked constraints. Change the name of the `walkConstraints` function to `cleanConstraints`.

In `packages/inferencer/tests/prim-neq.test.ts`, replace every `it.fails` with `it`. Add tests that query `prim_neq` directly as a top-level relation. Cover equal ground terms, different ground terms, and two unbound variables. Assert the constraint is present only for the unbound case.

#### Acceptance criteria of phase 1

**Agent-tested**

- `npm test -- --project inferencer` passes.
- Every former `it.fails` test in `packages/inferencer/tests/prim-neq.test.ts` now runs as a normal test and passes.
- The diff contains no changes outside `packages/inferencer`.
- `npm run lint`, `npm run fmt`, and `npm run fmt:check` pass.

**Test-in-code-tested**

- A `prim_neq` premise logs a derivation node with `relation` equal to `prim_neq`, `rule` equal to `prim`, empty `premises`, and resolved `args`.
- Ground different terms produce a solution with `constraints.neq` empty.
- Ground equal terms produce no solution.
- Two unbound query variables produce a solution with one resolved `neq` constraint.
- A constraint that becomes trivially true after later bindings is absent from the result.
- A constraint with one unbound side remains, with the bound side resolved.
- A top-level `prim_neq` query works with ground and unbound arguments.

### Phase 2: Add validator support

#### Goal of phase 2

Teach the validator that `prim_neq` is a built-in relation. Reject a user-defined relation with that name. Validate constraint terms in QueryResult files.

#### Description of phase 2

In `packages/validator/modules/only-defined-relations.ts`, accept `prim_neq` in `onPremise` and `onQuery`. Add an `onRelation` check that rejects a System relation named `prim_neq` with a new reserved-name error. Export the new check so the fused traversal includes it.

In `packages/validator/modules/correct-argument-count.ts`, make `prim_neq` expect two arguments in premises. Add an `onQuery` handler that checks the two-argument rule when the query relation is `prim_neq`. Leave existing query handling for other relations unchanged.

In `packages/validator/module-common.ts`, extend the location path types for query-result constraint terms.

In `packages/validator/driver.ts`, traverse `solution.constraints.neq` in `validateQueryResult`. Validate both terms with the same derivation-term checks used for solution variables.

Create `packages/validator/tests/prim-neq.test.ts`. Use the public functions from `packages/validator/lib.ts`. Build minimal System, Query, and QueryResult fixtures.

Run `npm run codegen` after the module edits. Commit the generated `fused.ts`.

#### Acceptance criteria of phase 2

**Agent-tested**

- `npm test -- --project validator` passes.
- `npm run codegen` completes and the generated `packages/validator/codegen/fused.ts` contains the new checks.
- `npm run lint`, `npm run fmt`, and `npm run fmt:check` pass.

**Test-in-code-tested**

- A premise that calls `prim_neq` with two in-scope terms has no diagnostics.
- A premise that calls `prim_neq` with fewer or more than two arguments has a diagnostic.
- A Query whose relation is `prim_neq` with two arguments has no diagnostics.
- A Query whose relation is `prim_neq` with the wrong number of arguments has a diagnostic.
- A System that declares a relation named `prim_neq` has a diagnostic.
- An undefined relation name in a premise or query still has a diagnostic.
- A QueryResult with valid `constraints.neq` terms has no diagnostics.
- A QueryResult with an invalid constraint identifier has a diagnostic.

### Phase 4: Render `prim_neq` in TeX

#### Goal of phase 4

Make TeX output and derivation trees handle the built-in relation without a System relation definition.

#### Description of phase 4

Make `extractDerivationTeX` tolerate `prim_neq` specifically, using its dedicated relation (via `commandOf`) for output. The rule id is `prim`, with TeX label `\neq` (rendered like `[\neq]`, similar to other rules)

Extend `packages/tex-extractor/tests/derivation.test.ts` with tests for the macro and for a derivation tree that contains a `prim_neq` node. Also cover a System rule whose premise is `prim_neq`, because the rule macro renders the premise relation.
